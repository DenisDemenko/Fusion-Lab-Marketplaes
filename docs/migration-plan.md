# План міграції: злиття старого сайту, маркетплейсу і Book_Creality

Узгоджено через два раунди уточнень 2026-08-29. Цей документ — план робіт;
обґрунтування архітектурних рішень піде в ADR 0007 (перше завдання плану).

Мета: звести три системи в один продукт для реальних користувачів —
статичний грантовий сайт (`site/`), маркетплейс (`marketplace/`) і
AI-конструктор книг Book_Creality — зберігши робочий код кожної.

## Прийняті рішення

| Питання | Рішення |
|---|---|
| Глибина злиття з Book_Creality | **Окремий сервіс + SSO + єдиний домен** (не переписуємо 62k рядків) |
| Автентифікація | **Firebase Auth** (та, що в маркетплейсі). Nova втрачає власні паролі/сесії |
| Ролі | 8 ролей, **одна на користувача**, обирається при реєстрації; адмін точково коригує права |
| Відео курсів | **YouTube unlisted**, гейтинг за наявним `Entitlement` |
| Дизайн-система | Застосовуємо до **всіх** сторінок; акцент — за категорією лістингу |
| Логотипи УКФ/ЄС | **Прибираємо** |
| Підписки | Переносимо для викладачів, письменників, експертів, маркетологів, студентів |
| Дедлайн | Немає |

## Що вже зроблено (не входить в обсяг)

Перевірено в коді перед плануванням — це економить значну частину роботи:

- **Усі 10 курсів уже в маркетплейсі** зі структурою модулів, занять, цілей,
  тем, практики й проєктів. Текст і структура збережені — переносити нічого.
- **`Entitlement`** уже працює: відкриває завантаження платних файлів після
  оплати. Той самий механізм візьме на себе гейтинг відео.
- **Медіа-інфраструктура** готова: `MediaAsset` з `kind` (cover/attachment) і
  `access` (public/entitled), завантаження через `POST /seller/listings/:id/media`,
  UI-компонент `ListingMediaManager`. Обкладинки курсів лягають сюди без нової
  підсистеми — потрібне лише розширення під зображення уроків.
- **i18n UA/EN** на всіх 27 маршрутах — нові сторінки просто дотримуються патерну.
- **API-міст** `POST /bridge/books` уже публікує книги з Nova в каталог.

### Фаза A — Фундамент: ролі й права ✅ завершено 2026-08-30

Йшла першою, бо від матриці прав залежать усі наступні фази. Деталі рішень —
[`docs/adr/0007-role-permission-model.md`](adr/0007-role-permission-model.md).

- [x] **A0.** ADR 0007: модель ролей і прав, ґейт `sales:access` за
      `salesApproved`, `roleChosenAt` для одноразового самовибору.
- [x] **A1.** `UserRole` розширено з 3 до 8: `buyer`, `seller`, `admin`,
      `writer`, `expert`, `sales_manager`, `instruction_engineer`, `student`.
- [x] **A2.** Матриця прав — з відхиленням від початкового формулювання:
      каталог прав (`Permission`) лишився в коді (`src/auth/permissions.ts`),
      **не** окремою таблицею — жоден екран не дає адміну вигадати нове
      право на льоту, лише дозволити/заборонити вже наявне конкретній
      людині. У БД — тільки персональні відхилення
      (`UserPermissionOverride`), і фактичний ґейт `sales:access` за
      `User.salesApproved`, що закриває ризик нижче. Обґрунтування — ADR 0007.
- [x] **A3.** Guard-шар — з відхиленням: `RolesGuard`/`@Roles('admin')` на
      наявних адмінських маршрутах **не чіпали** (уже коректні й стабільні,
      тотальний рефакторинг ризикував регресією без функціональної
      потреби). Новий `PermissionsGuard`/`@RequirePermissions(...)` —
      адитивний шар для тонких прав нових ролей (`POST /me/role`,
      `PATCH /admin/users/:id/permissions`, `.../sales-approval`).
- [x] **A4.** `POST /me/role` (одноразовий самовибір) + `RoleGate` на
      фронтенді (блокує застосунок до вибору ролі для нового акаунту) +
      розширена `/admin/users` (роль, перемикач `salesApproved`,
      розгортна панель ефективних прав і оверрайдів).

**Знайдено й виправлено під час реалізації, не в початковому плані:**
свіжий рядок `User` створюється зі схемним дефолтом `buyer` ще до вибору
ролі — без окремого прапорця `RoleGate` заблокував би **і сідованого
адміна** на екрані вибору ролі назавжди. Виправлено `roleChosenAt` +
бекфіл-міграцією для наявних акаунтів + `prisma/seed.ts` тепер сам
проставляє це поле для адміна/продавця лабораторії.

**Права по ролях (реалізовано):**

| Роль | Може |
|---|---|
| Письменник (`writer`) | `books:write` + `sales:access` (за схваленням) |
| Менеджер продажів (`sales_manager`) | `sales:access` (за схваленням) — без `listings:write` |
| Експерт (`expert`) | `listings:write` — створює курси через **наявну** форму лістингу в кабінеті продавця. Підтверджено e2e-тестом: кабінет продавця гейтиться за `SellerProfile.status`, не за роллю, тож жодних змін коду не знадобилось |
| `instruction_engineer`, `student` | порожній пресет — права не визначені планом, додаються через `UserPermissionOverride` вручну до узгодження |

✅ **Ризик закрито:** `sales:access` пропонується пресетом ролі, але реально
працює лише після `PATCH /admin/users/:id/sales-approval` — та сама межа
довіри, що вже існує для `SellerProfile.status`. Адмін виключений з цього
ґейту явно (роль і так означає повну довіру).

**Перевірено:** 12 нових e2e-тестів (самовибір ролі, одноразовість,
ґейт `sales:access`, оверрайди прав у обидва боки, `expert` через наявний
кабінет продавця), повний прогін 84 e2e + 10 unit — усі зелені; typecheck,
eslint, build обох застосунків — чисті.

### Фаза D — Курси: відео, прогрес, зображення `M` — завершено 2026-08-30

- [x] **D1.** `videoUrl` додано в `shared-types` (`CourseLesson.videoUrl`),
      і — окремо від початкового формулювання плану — зроблено **редагованим
      через текстовий формат програми курсу**, не лише читаним із seed-даних:
      рядок `video: <посилання>` одразу під заняттям (`curriculum-text.ts`).
      **Знайдено й закрито дірку безпеки під час реалізації:** публічний
      `GET /catalog/:slug` віддавав `videoUrl` у сирому JSON будь-кому
      неавтентифікованому — той самий клас проблеми, що вже розвʼязаний
      для `lockedMedia`, просто ще не застосований до відео. Тепер
      `toListingDetail` стрипає `videoUrl` (`stripVideoUrls` у
      `listing.mapper.ts`), лишаючи заголовки занять видимими.
- [x] **D2.** Гейтинг за `Entitlement`: `GET /me/library/:slug` (уже існував
      бекенд-методом, але жодна сторінка фронтенду його не використовувала)
      віддає повну програму з `videoUrl` лише після перевірки
      `Entitlement`; нова сторінка `/account/library/[slug]` рендерить
      `youtube-nocookie`-плеєр. Без покупки — 404, не урізана відповідь.
- [x] **D3.** `LessonProgress` (userId × listingId × moduleIndex ×
      lessonIndex — лістинги адресуються позицією в JSON-масиві уроків,
      не окремим id, бо `curriculum` — суцільна JSON-колонка). Чекбокс
      «Переглянуто» на сторінці курсу, індикатор «Пройдено X з Y занять».
      `POST /me/library/:slug/progress` — той самий ґейт за `Entitlement`.
- [x] **D4.** Новий `MediaKind.gallery` — публічні зображення лістингу
      понад одну обкладинку. Розширено `ListingMediaManager` (секція
      «Додаткові зображення») і сторінку деталей каталогу (стрічка
      мініатюр). Завжди `access: public`, незалежно від того, що передав
      клієнт — та сама причина, що й для обкладинки.
- [x] **D5.** З `Рисунки/` зіставляється однозначно лише набір
      `30_Day_UAV_Engineering_Mastery_-_Slide_*.png` → курс `uav-mastery`
      (11 файлів реально існує, не 12 — Slide_11 відсутній). Автоматизовано
      в `prisma/seed.ts` (`seedUavGallery`): копіює файли в сховище,
      створює `MediaAsset` записи, ідемпотентно (пропускає, якщо галерея
      вже наповнена), і **не падає в проді** — тека `Рисунки/` існує лише
      на цій машині поза репозиторієм, перевірка `existsSync` пропускає
      крок, якщо її немає. Решту ~120 файлів (без чіткої прив'язки до
      курсу) заливаєш вручну через D4.

⚠️ **Чесно про захист відео:** YouTube unlisted — це приховування посилання,
не захист. Хто отримав лінк, дивитиметься завжди і зможе переслати. Гейтинг
у застосунку прибирає посилання з очей некупивших (і тепер — з самої
відповіді API, не лише з інтерфейсу), але не робить відео приватним. Якщо
колись знадобиться справжній захист — перезаливка на Mux/Vimeo Pro/
S3+CloudFront із підписаними URL; `youtubeEmbedUrl()` — єдине місце,
де провайдер конкретизується, тож заміна не зачепить решту D1–D3.

**Перевірено:** 6 нових e2e-тестів (стрипання videoUrl з публічної
відповіді, видача повної програми лише за наявності Entitlement,
незнайомець ніколи не бачить сутність, тогл прогресу в обидва боки з
ідемпотентним upsert, відмова в записі прогресу без покупки, публічність
gallery-зображень з розділенням від платних вкладень) + повний прогін —
усі зелені; typecheck/eslint/build обох застосунків чисті; вживу в
браузері підтверджено рендер 11 галерейних зображень на сторінці
`uav-mastery`.

      момент запрошення (`Team.memberCount`), не в момент підтвердження —
      інакше власник міг би розіслати необмежено запрошень, а прийняти

      upsert) вперед гарантує, що повторне запрошення тієї самої людини
      падає на унікальному індексі до того, як гард на місткість взагалі
      побачить запит — тож не може подвійно зарезервувати місце вже зайнятій

### Фаза H — Права нових ролей і запрошення менеджера продажів `M` — маркетплейс і ґейти Nova завершені 2026-08-30; попереду H2.4 (кнопка), H4.3 (квота), H5.1 (відповідність ролей)

Закриває відкрите питання №1 (права `instruction_engineer` і `student`) і
частину №4 (апрув ролей, повʼязаних із продажами). Фаза A завела вісім ролей,
але каталог прав лишився з трьох позицій, а пресети двох ролей — порожніми.

#### H0. Що доводиться додати до каталогу прав

Наявні три права (`listings:write`, `sales:access`, `books:write`) не
розрізняють того, що вимагає нова постановка: публікацію всередині Nova від
публікації на зовнішніх майданчиках, і право витрачати гроші на генерації від
права підставляти власні ключі. Каталог розширюється з 3 до 7:

| Право | Значення |
|---|---|
| `listings:write` | *(наявне)* створення й редагування лістингів у кабінеті продавця |
| `sales:access` | *(наявне)* власна вітрина: кошик, свої замовлення, свої товари |
| `books:write` | *(наявне)* складання й редагування текстів у Nova |
| `publishing:nova` | публікація в межах Nova — зробити книгу чи інструкцію доступною в каталозі |
| `publishing:external` | зовнішні майданчики: Amazon KDP та Etsy, включно з OAuth-підключенням крамниці |
| `images:generate` | витрачати платні генерації зображень |
| `keys:manage` | вводити **власні** секретні ключі AI-провайдерів |

**Чому Etsy OAuth потрапив у `publishing:external`, а не в `keys:manage`.**
Підключення крамниці — це OAuth-токен конкретного майданчика, який видає сам
Etsy і який система вже шифрує у себе. Секретні ключі провайдерів — це
облікові дані стороннього AI-сервісу, які користувач вводить руками. Різні
межі довіри, тож і права різні: менеджер продажів мусить підключити крамницю,
але не мусить мати доступу до ключів OpenAI чи Gemini.

#### H1. Повна матриця прав

Матриця свідомо наведена цілком, а не лише зміненими рядками — щоб її можна
було коригувати після реалізації, не відновлюючи контекст по шматках.

| Роль | `listings:write` | `sales:access` | `books:write` | `publishing:nova` | `publishing:external` | `images:generate` | `keys:manage` |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| `buyer` — покупець | — | — | — | — | — | — | — |
| `seller` — продавець | ✅ | — | — | — | — | — | — |
| `admin` — адміністратор | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `writer` — письменник | — | ✅¹ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `expert` — експерт | ✅ | — | — | — | — | — | — |
| `sales_manager` — менеджер продажів | — | ✅¹ | — | ✅ | ✅ | — | — |
| `instruction_engineer` — інженер зі складання інструкцій | — | — | ✅ | ✅ | — | ✅ | ❌² |
| `student` — студент | — | — | ✅ | ✅ | — | ✅ | ❌² |

¹ Пресет лише **пропонує** право; фактично воно вмикається після
`PATCH /admin/users/:id/sales-approval` (ґейт із Фази A, ADR 0007).

² Не просто відсутнє, а свідомо заборонене: послуги цим ролям надає Nova
своїми ключами (H4).

**Письменник лишається надмножиною менеджера продажів.** Це не недогляд, а
збереження рішення П16 із Фази A: письменник делегує продажі, але не втрачає
права робити їх сам.

#### H2. Менеджер продажів — тільки за запрошенням

`sales_manager` не можна обрати самому: ні при реєстрації, ні в профілі.
Єдиний шлях — лист на пошту, який письменник надсилає окремою кнопкою.

- [x] **H2.1.** Константа `SELF_SELECTABLE_ROLES` у `src/auth/permissions.ts`;
      `POST /me/role` відхиляє все, чого в ній немає. `sales_manager` і `admin`
      до неї не входять.
- [x] **H2.2.** `POST /me/sales-manager-invites` — письменник вводить пошту,
      система створює запрошення з токеном і строком дії 7 днів.
- [x] **H2.3.** `POST /sales-manager-invites/:token/accept` — отримувач
      приймає, роль призначається системою, а не вибором користувача.
- [ ] **H2.4.** Кнопка «Запросити менеджера продажів» у кабінеті письменника.

**Зразок уже є в Nova.** `POST /api/collaboration/invite` робить рівно це для

(бо ролі живуть там), а не вигадує другий механізм запрошень.

#### H3. Інженер зі складання інструкцій і студент

Обидві ролі отримують однаковий пресет: складання текстів, публікація в межах
Nova, генерація зображень. Різниця між ними — не в правах, а в квотах і
подальшій диференціації, тож пресет спільний.

- [x] **H3.1.** Пресети `instruction_engineer` і `student`:
      `books:write`, `publishing:nova`, `images:generate`.
- [x] **H3.2.** `publishing:external` їм **не** видається: зовнішні майданчики —
      привілей менеджера продажів і письменника. Якщо після реалізації
      виявиться, що інженер має публікувати інструкції на Etsy сам — це

#### H4. Заборона власних ключів і хто за це платить

- [x] **H4.1.** `keys:manage` відсутнє в пресетах обох ролей; маршрути

- [x] **H4.2.** AI-виклики цих ролей ідуть на серверних ключах Nova.

⚠️ **Ризик, який це відкриває.** Якщо `student` лишиться вільним для

- [ ] **H4.3.** Квота генерацій для `instruction_engineer` і `student` через

#### H5. Відповідність ролей між маркетплейсом і Nova

Nova має власну рольову модель (`src/types.ts`: `admin`, `writer`, `designer`,
`translator`, `publisher`, `reader`, `guest`) і власні прапорці прав. Після
злиття джерелом істини стає роль маркетплейсу, а роль Nova виводиться з неї:

| Роль маркетплейсу | Роль у Nova | Обґрунтування |
|---|---|---|
| `admin` | `admin` | повний доступ в обох системах |
| `writer` | `writer` | пряма відповідність |
| `instruction_engineer` | `writer` | ті самі дії з текстом, різниця лише у квотах і ключах |
| `student` | `writer` | те саме |
| `sales_manager` | `publisher` | роль Nova вже про верстку, аудит Amazon KDP та експорт |
| `buyer`, `seller`, `expert` | `reader` | доступ до Nova лише на перегляд |

- [ ] **H5.1.** Функція відображення ролей + похідні прапорці `RolePermission`.
- [x] **H5.2.** Пресет `publisher` у Nova доповнюється правом публікації —
      зараз воно там не виражене окремим прапорцем.

**Знайдено й виправлено під час реалізації, не в початковому плані:**
`SELF_SELECTABLE_ROLES` існувала дублем — локальною константою в
`app.controller.ts` — і **містила `sales_manager`**, тобто роль можна було
просто обрати в профілі, повз будь-яке запрошення. Зведено до однієї
константи в `permissions.ts`, роль прибрано, поведінку закріплено тестом.

⚠️ **Пастка Prisma, яку варто памʼятати.** Автогенерована міграція для
`SalesManagerInvite` містила `DROP INDEX` на обидва пошукові індекси
`Listing`: вони створені сирим SQL, тож Prisma вважає їх дрейфом
(`searchVector` — `Unsupported("tsvector")`, `gin_trgm_ops` у схемі не
виражається). Перший прогін встиг їх дропнути. Відновлено окремою
міграцією `20260829223000_restore_listing_search_indexes`. Кожну наступну
згенеровану міграцію треба вичитувати на ці DROP-и.

**Перевірено:** 7 нових e2e на потік запрошення (прийняття, чужа пошта,
одноразовість, не-письменник, дубль, відкликання, протермінування) +
тест на заборону самовибору ролі; `roles-permissions` 13/13,

**Про повний прогін:** 119 тестів, у повному серійному прогоні
нестабільно падають 2–3 набори з `Exceeded timeout ... for a hook` на
`resetDatabase`. Набори щоразу різні, кожен в ізоляції зелений, а логи
Postgres показують `checkpoint ... sync=166 s` — це повільний диск Docker
на WSL2 після збою, не регресія.

**Знайдено під час реалізації ґейтів Nova.** У Nova **дві незалежні
таблиці прав**: клієнтська `src/utils/rbac.ts` (повний опис ролей) і

`requirePermission`. Правка лише клієнтської дає 403 на роль, якій
інтерфейс право показує — саме так і сталось, спіймано тестами ключів.
Обидві таблиці тепер містять `canPublish`, `canPublishExternal` і
`canManageApiKeys`, а коментар у `auth.ts` попереджає про дублювання.

**Колізія, розвʼязана на користь матриці H1:** роль `publisher` у Nova
мала вкладку `api-keys`, хоча відповідний їй `sales_manager` права на
власні ключі не має. Право вимкнено — послуги надає Nova.

**Перевірено:** 21 маршрут закрито (12 `canPublish`, 6
`canPublishExternal`, 3 `canManageApiKeys`); 5 нових тестів стережуть сам
ґейт — читач отримує 403 на публікацію й на Etsy, видавець 200 на обох;
повний прогін Nova 89/0, typecheck чистий.

## Порядок і залежності

```
A (ролі) ──┬── D (курси)
           ├── E (підписки) ──── G5 (KDP/Etsy для Pro/Ultra)
           ├── F1 (команди — без бейджа підписки, не блокується E)
           ├── F2 (бронювання)
           └── G1 (Firebase у Nova) ── G3 (спільний домен) ── G2 (SSO) ── G4

B (дизайн) — паралельно, не блокує нікого після B1–B4
C (hero)   — залежить лише від B1–B2 (токени й шрифти)
```

**G3 перед G2** (уточнено при реалізації, у початковому плані було навпаки):
стан входу Firebase браузер тримає окремо для кожного origin, тож єдина
сесія неможлива, доки застосунки на різних адресах. Спільний домен — це
передумова SSO, а не окрема косметична задача.

Фаза A йде першою і одна. Далі B і C можна вести паралельно з D.
E — лише перед G5 (F1 збудовано без бейджа активної підписки, тож більше не
залежить від E — див. Фазу F).

## Що пропоную відкласти

Ти обрав «реальний продукт важливіший, але портфоліо теж» і попросив назвати,
що ріжеться без болю. Мої кандидати:

1. **Інтерфейс конструктора курсів** (уже погоджено окремим пакетом) — експерт
   поки створює курс через наявну форму лістингу в кабінеті продавця.
2. ~~F1 «Команди STEAM»~~ — збудовано (без бейджа активної підписки), див.
   Фазу F. Виявилось, що не залежить від ядра маркетплейсу так, як здавалось
   спочатку — команда без бейджа все одно читається як звичайний каталог.
3. **G5 KDP/Etsy як платний плагін** — інтеграції вже працюють у Nova як є.
   Гейтинг за підпискою можна ввімкнути пізніше, коли Фаза E стабілізується.
4. **B5 (редизайн 27 сторінок)** — не відкладати цілком, а вести поступово:
   B1–B4 дають нову систему, сторінки переводимо хвилями.

Якщо погодишся хоча б на 1–3, обсяг першої ітерації падає приблизно на третину
без втрати робочого продукту.

- **E2 (рекурентні платежі)** — LiqPay-підписки поводяться інакше за разові

- **Годинник хоста** — виправлено разово 2026-08-29, але **причина лишилась**:
  служба `w32time` на машині вимкнена й не стартує (`0x80070426`), тож
  `w32tm /resync` не спрацює. Годинник виставили з HTTP-заголовка `Date`
  (`Set-Date`). Очікуй, що він знову «втече» — і що це знову проявиться як
  незрозуміла відмова Firebase-токенів. Надійне рішення — полагодити службу
  (`Set-Service w32time -StartupType Manual; Start-Service w32time`).

## Відкриті питання

1. ~~Права для ролей `instruction_engineer` і `student`~~ — вирішено: спільний пресет `books:write` + `publishing:nova` + `images:generate`, без права на власні ключі провайдерів (Фаза H, повна матриця — H1).

5. Чи потрібна окрема форма "зв'яжіться з нами" поза бронюванням занять
   (напр. для співпраці/медіа-запитів) — F3 з початкового плану вважали
   поглиненою реальним бронюванням (Фаза F2), бо тодішня F3 була про запис
   на заняття, який тепер має справжній `/schedule`.
