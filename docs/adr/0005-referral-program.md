# ADR 0005: Реферальна програма — доменна модель

## Статус

Прийнято — 2026-08-29

## Контекст

`CONTEXT.md` називає реферальну програму «флагманським кейсом для повного
доменного моделювання», і не випадково: цільова вакансія прямо згадує
"реалізувати referral system для marketplace" як приклад задачі. Це
означає, що ця фіча має демонструвати не просто CRUD, а свідомі рішення
щодо станів, атомарності та захисту від зловживань — саме те, що
відрізняє портфоліо-проєкт від навчального прикладу.

Специфікація з `CONTEXT.md`, дослівно: «Покупець запрошує іншого
користувача через реферальне посилання; за перше замовлення запрошеного
запрошувач отримує бонус (у loyalty-балах)».

## Рішення

### Модель: одна сутність, а не подія

`Referral` — один рядок на **запрошеного** користувача
(`@unique referredId`), а не журнал подій "хтось перейшов за посиланням".
Це свідомий вибір: питання, яке система має відповідати найчастіше —
«чи вже підв'язаний цей акаунт до когось?» — стає простим `findUnique`
замість `ORDER BY ... LIMIT 1` по журналу. Ціна цього рішення: одна
людина може мати лише одного запрошувача за все життя акаунту, що
збігається з реальною семантикою "хто мене привів" — вона не повторюється.

### Стани: claim → award, кожен один раз

```
[немає Referral] --claim--> [bonusAwarded=false] --перше оплачене замовлення--> [bonusAwarded=true]
```

`claim()` (`POST /referrals/claim`) створює звʼязок. Нарахування бонусу
відбувається не тут, а пізніше, всередині `OrdersService.markPaid` —
`ReferralsService.maybeAwardBonus()` викликається в тій самій транзакції,
що переводить замовлення в статус `paid`. Це навмисно, з двох причин:

1. **Атомарність.** Якщо нарахування бонусу впаде через помилку, весь
   платіж має відкотитися разом з ним — гроші реально надійшли, тож
   часткова відмова (замовлення оплачене, а бонус не нарахований) була б
   гіршим станом, ніж повний rollback і повторна спроба через ретрай
   LiqPay-колбека.
2. **Ідемпотентність за конструкцією.** LiqPay ретраїть колбек; `markPaid`
   вже ідемпотентний (перевіряє `status === 'paid'` на вході). Захист від
   подвійного нарахування бонусу — умова `bonusAwarded: false` у самому
   `updateMany`, а не окрема перевірка "чи вже нараховано" перед записом:
   `updateMany` з умовою в `WHERE` атомарно вирішує "перегони" між двома
   паралельними спробами оплатити те саме замовлення, тоді як
   read-then-write завжди залишає вікно для дублювання.

"Перше замовлення" визначається як `count(Order WHERE buyerId = X AND
status = 'paid') === 1` **всередині тієї самої транзакції**, вже після
того, як поточне замовлення отримало статус `paid`. Це означає: якщо
рахувати "один", то це замовлення й було першим оплаченим — без окремого
прапорця "перша покупка" на User, яких довелося б синхронізувати.

### Валюта бонусу: loyalty-бали, не окремий гаманець

`CONTEXT.md` прямо каже "бонус (у loyalty-балах)" — тому бонус
проводиться через уже наявний `LoyaltyService.awardReferralBonus()`,
який пише в той самий `LoyaltyTransaction`-журнал, що й кешбек. Один
журнал, один баланс, одна модель "звідки взялися бали" — реферальна
система не потребує власного класу активів.

### Захист від зловживань: вікно для claim закривається першою покупкою

Реферальний код можна застосувати (`claim`) будь-коли **до** першої
оплаченої покупки, не обовʼязково відразу після реєстрації — повільна
мережа чи бага фронтенду в день реєстрації не мають назавжди коштувати
людині втраченого реферала. Але після першої оплаченої покупки —
`claim` відмовляє (409). Без цього обмеження хтось міг би: купити щось
без посилання, а потім заднім числом "прив'язати" вже здійснену покупку
до чийогось коду, штучно генеруючи бонуси без жодного реального ефекту
від запрошення.

Самореферал (referrerId === referredId) відхиляється explicit-перевіркою
(400), а не покладанням на те, що користувач "просто не знатиме власний
код" — код видно в `/referrals/me`, тож перевірка мусить бути реальною.

## Альтернативи

1. **Бонус і запрошеному, і запрошувачу (двосторонній).** Відхилено:
   `CONTEXT.md` специфікує бонус лише запрошувачу. Двосторонній бонус —
   логічне розширення для Фази 3, якщо знадобиться, але не частина
   поточної специфікації.
2. **Реферальний код як звичайний промокод (знижка на перше замовлення).**
   Відхилено: промокод — це знижка на суму, не звʼязок між двома
   акаунтами. Змішування цих понять ускладнило б і `PromoCode` (довелося
   б додавати "промокод, привʼязаний до конкретного referrer"), і
   Referral (довелося б відстежувати використання як звичайний
   redemption). Окрема сутність — чистіша модель для обох.
3. **Нарахування бонусу одразу при claim, а не при першій оплаті.**
   Відхилено: суперечить самій специфікації ("за перше замовлення") і
   відкриває очевидний зловжив — claim без наміру щось купувати, просто
   заради бонусу запрошувачу.
4. **Журнал подій замість однієї сутності на referredId.** Відхилено
   вище (розділ "Модель") — ускладнює найчастіший запит заради гнучкості,
   якої тут ніхто не просив (одна людина не може мати кількох
   запрошувачів одночасно за задумом).

## Наслідки

- Немає багаторівневого реферала (запрошений запрошує когось ще, і
  оригінальний запрошувач теж щось отримує) — свідомо поза межами
  специфікації; якщо знадобиться, `Referral` вже має обидва боки
  звʼязку (`referrerId`/`referredId`), тож ланцюжок читається рекурсивним
  запитом без зміни схеми.
- Розмір бонусу (`REFERRAL_BONUS_POINTS = 500`) — константа в
  `LoyaltyService`, не налаштування в БД. Якщо знадобиться A/B-тестування
  розміру бонусу чи різні ставки для різних кампаній — це вже вимагає
  окремої моделі "реферальна кампанія", яку зараз створювати рано.
- `Referral.awardedAt` зберігається окремо від `bonusAwarded: true` для
  звітності (коли саме нарахували), хоча жодна поточна фіча цього поля
  ще не читає — дешево мати зараз, дорого мігрувати додавати пізніше.
