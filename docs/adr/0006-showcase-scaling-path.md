# ADR 0006: Шлях масштабування — AWS, пошук, event-driven, навантаження

## Статус

Задокументовано, не виконано — 2026-08-29. Це ADR "showcase"-типу: фіксує
свідоме рішення **не** робити описане нижче зараз, і що саме треба зробити,
коли зʼявиться реальна причина. Покриває всі чотири пункти Фази 3 з
`ROADMAP.md` одним документом, бо вони описують одну історію — як цей
MVP виріс би за межі поточного навантаження — а не чотири незалежні вибори.

## Контекст

Поточний прод (див. `README.md` → "Стан"): Vercel (web) + Railway (api +
Postgres). Один інстанс NestJS (`NestFactory.create` без кластеризації,
`apps/api/src/main.ts`), одна Postgres-база. Конкретні факти, що визначають
усе нижче:

- **Пошук** — Postgres full-text (`tsvector` generated column + GIN-індекс
  + `pg_trgm` для fuzzy-збігів), без окремого пошукового рушія. Працює
  добре для каталогу в сотні-тисячі лістингів.
- **Черги/події — відсутні.** `docker-compose.yml` піднімає Redis
  (`redis:7-alpine`, порт 6379) і `.env.example` містить `REDIS_URL` — але
  жоден код їх не використовує. BullMQ не встановлено. Усе, що виглядає як
  "фонова робота" (нарахування loyalty-балів, реферальний бонус,
  сповіщення), виконується синхронно всередині Prisma-транзакції в
  `OrdersService.markPaid` (`apps/api/src/orders/orders.service.ts`),
  викликаної прямо з LiqPay callback (`apps/api/src/orders/payments.controller.ts`).
- **WebSocket без адаптера для кількох інстансів.** `ChatGateway` і
  `NotificationsGateway` (`apps/api/src/{chat,notifications}/*.gateway.ts`)
  використовують socket.io зі стандартним in-memory адаптером. Кімнати
  (`user:<id>`) існують лише в памʼяті одного процесу.
- **Немає rate limiting.** `@nestjs/throttler` не підключено ніде.
- **Пул зʼєднань Prisma** — `PrismaPg` (`apps/api/src/prisma/prisma.service.ts`)
  бере дефолтний розмір пулу `node-postgres` (10 зʼєднань на інстанс), явно
  не сконфігурований.

Ці факти — не недоліки MVP, а нормальний стан системи, розрахованої на
одного орендаря з помірним трафіком. Нижче — що ламається першим при
рості, і як це виправити.

## Рішення

### 1. Compute/дані → AWS (ECS/RDS/ElastiCache)

**Чому не зараз:** Railway + Vercel коштують $10–30/міс і не вимагають
DevOps-часу. AWS-еквівалент (ECS Fargate + ALB + RDS + ElastiCache +
NAT Gateway) — це вже $150–300+/міс мінімум навіть при нульовому трафіку
(NAT Gateway й ALB тарифікуються за години роботи, не за використання), і
години на Terraform/CDK, VPC, security groups. Для портфоліо-проєкту без
реального навантаження це витрата без користі, окрім демонстрації вміння.

**Цільова архітектура, коли причина буде** (ріст трафіку, вимога клієнта
щодо AWS, або compliance):

```
Route 53 → CloudFront (web static assets)
                ↓
        ALB → ECS Fargate (apps/web, Next.js standalone output)
                ↓
        ALB → ECS Fargate (apps/api, NestJS, 2+ таски за таргет-групою)
                ↓
   RDS PostgreSQL (Multi-AZ) ←→ RDS Proxy (пул зʼєднань, див. п.4)
                ↓
   ElastiCache Redis (заміна Railway/docker-compose Redis)
                ↓
   S3 (медіа-файли замість локального storage — див. apps/api/src/storage)
```

- **ECS замість EKS** — Kubernetes невиправданий для 2 сервісів і команди з
  однієї людини; ECS Fargate дає той самий "не керуй нодами" досвід
  з набагато меншою операційною поверхнею.
- **RDS замість самокерованого Postgres на EC2** — керовані бекапи,
  Multi-AZ failover; ціна виправдана саме для продової бази, на відміну
  від ALB/NAT, які коштують незалежно від навантаження.
- **Секрети** — AWS Secrets Manager замість Railway/Vercel env vars;
  `LIQPAY_PRIVATE_KEY`, `FIREBASE_SERVICE_ACCOUNT`, `DATABASE_URL` — усе,
  що зараз лежить у Vercel/Railway дашбордах.
- **Міграція поетапна, не "big bang":** спочатку RDS (з тим самим
  `DATABASE_URL`-контрактом, Prisma не бачить різниці), потім ECS для API
  (web лишається на Vercel — CDN + edge-мережа Vercel сильніша за
  CloudFront+S3 для Next.js конкретно), і лише потім, якщо є причина,
  переносити й web.

### 2. Пошук → Elasticsearch/OpenSearch

**Чому не зараз:** Postgres FTS (`Listing.searchVector`, див. міграцію
`20260828163354_phase1_marketplace`) покриває точний і fuzzy пошук по
каталогу без окремої інфраструктури для синхронізації. OpenSearch додає
цінність тільки коли зʼявляється те, чого Postgres не робить добре:
faceted-фільтри з агрегаціями по великій кількості атрибутів одночасно,
типографічно толерантний пошук на рівні цілого речення (не лише окремих
слів через `pg_trgm`), або каталог у сотні тисяч+ лістингів, де GIN-індекс
починає програвати за latency.

**Тригер міграції:** p95 latency `/catalog?q=` вище ~200мс під реальним
навантаженням, або вимога до фасетного пошуку (фільтр по 5+ атрибутах з
підрахунком кількості для кожного варіанту в реальному часі).

**Шлях міграції:** Postgres лишається джерелом істини (не дублювати
domain-логіку). OpenSearch — read-only проєкція:

1. `ListingIndexedEvent` публікується при create/update/publish лістингу
   (природно лягає на чергу з п.3 — консьюмер пише в OpenSearch).
2. `GET /catalog` починає читати з OpenSearch, коли `q` заданий; без `q`
   (перегляд каталогу за категорією) лишається на Postgres — простий
   `WHERE`, індекс не потрібен.
3. Reindex-скрипт для початкового наповнення й для відновлення після
   розбіжності.

### 3. Event-driven: BullMQ (наявний Redis) → Kafka/RabbitMQ

**Крок 1, найближчий — BullMQ.** Redis вже піднятий (`docker-compose.yml`,
`REDIS_URL` в `.env.example`), просто не використаний. Найперший
реальний кандидат — сам LiqPay callback: `PaymentsController.liqpayCallback`
зобовʼязаний відповісти банку 200 швидко (LiqPay ретраїть годинами
інакше), а зараз усередині нього синхронно виконується вся `markPaid`
транзакція (нарахування loyalty, реферальний бонус, сповіщення продавцю).
За нинішнього навантаження це не проблема (транзакція — мілісекунди), але
це природний шаблон "прийняв → підтвердив → віддав у чергу", який
масштабується лінійно, коли транзакція обросте додатковою роботою
(наприклад, надсилання email-квитанції, синхронізація з бухгалтерською
системою). Інші кандидати: пакетна обробка `Payout.record` для багатьох
продавців одночасно, and reindex-джоби для п.2.

**Крок 2 — Kafka/RabbitMQ.** Виправдані лише коли зʼявляється **другий
споживач** тієї самої події з іншого сервісу (BullMQ — це черга завдань
для одного застосунку, а не шина подій для кількох). Реалістичний
кандидат для цього проєкту — окремий analytics/reporting-сервіс, що
слухає `OrderPaid`/`ListingPublished` незалежно від `apps/api`, або
розширення мосту з Book_Creality (`docs/adr/0001-two-systems-with-api-bridge.md`)
до двостороннього — зараз API дзвінок один напрямок (Marketplace →
Book_Creality за даними книги), подієва шина знадобилася б, якби
Book_Creality мав сповіщати Marketplace про власні зміни push, а не чекати
на pull. RabbitMQ — простіший вибір за Kafka для цього масштабу
(одна команда, кілька consumer-груп, не потрібне довгострокове
event-sourcing чи replay), Kafka виправданий лише якщо реально зʼявиться
потреба в retention подій на тижні/місяці для reprocessing.

### 4. Навантажувальне тестування

**Методологія (не виконана, задокументована):** k6 або Artillery,
три сценарії за реалістичністю навантаження:

1. **Перегляд каталогу** (найчастіший шлях, без автентифікації) —
   `GET /catalog`, `GET /catalog/:slug` з varying `q`/`category`.
2. **Checkout** (найважчий по транзакційності) — `POST /cart`,
   `POST /orders/checkout`, паралельні спроби на той самий обмежений
   `stock` і той самий `PromoCode` з `maxRedemptions` — саме тут існуючі
   e2e-тести вже перевірили коректність (`updateMany`-guard), навантажувальний
   тест перевірив би не коректність, а **latency під конкуренцією за той
   самий рядок**.
3. **WebSocket fan-out** — N одночасних клієнтів у `/notifications`,
   виміряти latency сповіщення від `markPaid` до доставки клієнту.

**Передбачені вузькі місця (з аналізу коду, без запуску тесту):**

- **WebSocket-адаптер не переживе горизонтальне масштабування API.**
  Як тільки за ALB стане 2+ інстанси NestJS без `@socket.io/redis-adapter`,
  користувач, підключений до інстансу А, не отримає сповіщення, яке
  згенерував запит, оброблений інстансом Б — кімнати `user:<id>` існують
  лише в памʼяті процесу. Це перше, що ламається при масштабуванні, задовго
  до того, як CPU/DB стане вузьким місцем.
- **Пул зʼєднань Prisma множиться на кількість інстансів.** Дефолтні
  10 зʼєднань `node-postgres` × N інстансів API легко впираються в
  `max_connections` керованого Postgres (Railway/RDS без Proxy — типово
  ~100). Рішення при масштабуванні за межі 1 інстансу — RDS Proxy
  (AWS) або PgBouncer, не збільшення `max_connections` (не масштабується
  лінійно — кожне зʼєднання Postgres важке, окремий процес).
- **Немає rate limiting** — публічні ендпоінти (`/catalog`, LiqPay
  callback) не захищені від зловживання. `@nestjs/throttler` — перше,
  що варто додати перед будь-яким публічним навантажувальним тестом,
  інакше тест вимірює не застосунок, а відсутність захисту від нього ж.

## Альтернативи

1. **AWS App Runner замість ECS+Fargate+ALB** — простіше (Heroku-подібний
   досвід, без VPC/ALB-конфігурації), але менш гнучкий і по суті ближчий
   до Railway, ніж до "показати вміння працювати з AWS primitives" — для
   showcase-цілі ECS демонструє більше релевантних навичок.
2. **Aurora Serverless v2 замість RDS Provisioned** — варта розгляду саме
   для непередбачуваного/спайкового трафіку маркетплейсу (розпродажі,
   запуск нового курсу); відхилено з документації як default-рекомендацію,
   бо для стабільного базового навантаження provisioned RDS дешевший і
   передбачуваніший.
3. **Meilisearch/Typesense замість OpenSearch** — легші, простіші в
   експлуатації, гарний вибір для каталогу цього розміру. Не обрані як
   основна рекомендація тільки тому, що вакансія explicitly згадує
   Elasticsearch/OpenSearch — вибір тут керується вимогою портфоліо,
   не технічною перевагою.
4. **Kafka одразу, без проміжного BullMQ** — відхилено: немає другого
   споживача подій сьогодні, тож Kafka додав би операційну складність
   (Zookeeper/KRaft, партиції, consumer groups) без жодного use case,
   який BullMQ не покриває.

## Наслідки

- Жодна з чотирьох осей не блокує прод — поточна архітектура коректно
  обслуговує показане навантаження (перевірено 72 e2e + 10 unit тестами,
  `ROADMAP.md` → Фаза 1/2).
- Кожна вісь має явний тригер вище — рішення про реальну міграцію
  приймається за фактом (метрика/вимога), не наперед.
- Найдешевший наступний крок, якщо колись знадобиться демонструвати
  event-driven паттерн у дії — підключити BullMQ до вже наявного Redis
  для одного реального джоба (наприклад, email-квитанція після
  `markPaid`), це не вимагає нової інфраструктури, лише коду.
