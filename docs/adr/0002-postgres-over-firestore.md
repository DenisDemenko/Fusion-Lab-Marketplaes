# ADR 0002: PostgreSQL для каталогу/замовлень/платежів (не Firestore)

## Статус

Прийнято — 2026-08-25

## Контекст

Чинний Fusion Lab (`site/`) зберігає дані у Firebase Firestore (NoSQL,
document store). Цільова вакансія прямо вимагає PostgreSQL і розуміння
реляційного моделювання для scalable marketplace-архітектури. Дані
маркетплейсу — замовлення, order items, платежі, комісії, виплати,
loyalty-транзакції, реферали — за природою реляційні: множинні
зовнішні ключі, потреба в транзакціях (списання балів + створення
замовлення має бути атомарним), агрегації (сума комісій за період).

## Рішення

Каталог/замовлення/платежі/комісії/loyalty/referral переносяться на
PostgreSQL. Firebase Auth лишається для автентифікації (RFC — див. ADR
0003 не потрібен, це продовження вже наявної інтеграції, не новий вибір):
NestJS верифікує Firebase ID token через Firebase Admin SDK, а власна
таблиця `users` у Postgres зберігає domain-дані (роль, seller-профіль),
звʼязана з Firebase UID як зовнішнім ключем.

## Альтернативи

1. **Лишити Firestore для всього** — відхилено: не відповідає вимозі
   вакансії щодо PostgreSQL; транзакційна цілісність (списання
   loyalty-балів одночасно зі створенням замовлення) значно незручніша
   в Firestore, ніж у SQL-транзакції.
2. **Повністю власна auth-система замість Firebase Auth** — відхилено:
   Firebase Auth вже працює в чинному Fusion Lab, переписувати
   login/reset-password/email-verification з нуля не додає портфоліо-
   цінності порівняно з часом на це.

## Наслідки

- Гібридна модель: ідентичність користувача — у Firebase, домен-дані —
  у Postgres. Потрібен явний zsync-момент при першому вході (створення
  рядка `users` за Firebase UID, якщо не існує).
- Postgres розгортається локально через Docker Compose
  (`docker-compose.yml`), у проді — керований інстанс (Railway/Render на
  MVP-етапі, RDS — у showcase AWS-фазі).
