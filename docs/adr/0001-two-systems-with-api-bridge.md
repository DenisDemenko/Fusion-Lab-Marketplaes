# ADR 0001: Два окремі проєкти замість одного монолітного, зв'язані через API

## Статус

Прийнято — 2026-08-25

## Контекст

Є дві наявні кодові бази з різним призначенням:

- **Book_Creality** — зрілий AI SaaS для написання й публікації книг
  (React+Vite+Express+TS+SQLite), з реальними інтеграціями (LiqPay/PayPal,
  KDP/Etsy publishing, мультипровайдерний AI-чат).
- **Fusion Lab** (`site/`) — грантовий портал лабораторії (статичний
  HTML + Firebase), концептуально близький до маркетплейсу (курси, кошик,
  товари, підписка), але без Next.js/Node.js-бекенду, який вимагає цільова
  вакансія.

Мета — портфоліо з двох робочих систем, що демонструє: (а) складний AI SaaS
і (б) Marketplace/SaaS на Next.js+Node.js+PostgreSQL, як того прямо вимагає
вакансія.

## Рішення

Не зливати системи в один монорепо/монолітний продукт. Book_Creality
лишається окремим проєктом на своєму стеку. Новий Marketplace (`marketplace/`)
будується з нуля на Next.js+NestJS+PostgreSQL. Звʼязок — вузький API-міст:
Book_Creality публікує книгу → Marketplace показує її як лістинг у каталозі.

## Альтернативи

1. **Один об'єднаний Next.js-монорепо для всього** — відхилено: означало б
   переписати вже робочий і складний Book_Creality (редактор книг, AI-чат,
   publishing pipeline) на новий стек без функціональної потреби, лише
   заради єдності репозиторію. Дорого, без додаткової портфоліо-цінності.
2. **Розвинути тільки одну систему** — відхилено: гірше покриває вакансію
   (втрачається або AI SaaS кейс, або Marketplace кейс), і в користувача
   вже є суттєві напрацювання в обох.

## Наслідки

- Два репозиторії з незалежними CI/деплоями (Vercel+Railway для
  Marketplace; окремий процес для Book_Creality).
- API-міст — точка інтеграції, яку варто явно спроєктувати (auth між
  сервісами, формат DTO) і яка сама стає портфоліо-артефактом
  ("інтеграція зі сторонніми сервісами").
- Дублювання деяких паттернів (напр. AI-провайдер-шар) є прийнятним і
  свідомим — перевикористання коду між різними стеками (Express vs NestJS)
  все одно недоцільне.
